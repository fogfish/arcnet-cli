# Bug Report: MCP call logging omits filters and result size, and predates structured/colored output

**Type**: Spec gap (with a partial implementation-drift component)
**Severity**: Medium
**Feature**: 029-mcp-tool-metadata (MCP Tool Metadata Colocation) — cross-references 008-arc-serve-mcp (`arc serve`), the feature that owns the affected requirement
**Reported**: 2026-08-29
**Status**: Resolved
**Patched**: 2026-08-29
**Implemented**: 2026-08-29 — specs/008-arc-serve-mcp/tasks.md T043-T051

## Description

Every MCP tool handler in `cmd/arc/graph/` calls `logCall(tool, args string, err error)` (`cmd/arc/graph/serve.go`), which writes one plain `fmt.Fprintf(os.Stderr, ...)` line per call:

```go
func logCall(tool, args string, err error) {
	if err != nil {
		fmt.Fprintf(os.Stderr, "serve: %s %s error: %s\n", tool, args, err.Error())
		return
	}
	fmt.Fprintf(os.Stderr, "serve: %s %s ok\n", tool, args)
}
```

The user asks for three concrete improvements to this call-logging path:

1. Log the function (tool) name — already done.
2. Log the input arguments **including filters** — not done today for any of the four filter-accepting tools.
3. Log the **number of return elements** — not done today for any tool.
4. Keep each line short, but switch to structured logging via `log/slog`, using `github.com/fogfish/logger` (already present in the module cache at `v3.2.1`, not yet a `go.mod` dependency) for colored terminal output.

Concretely, per call site today (`grep -n "logCall(" cmd/arc/graph/serve_tool_*.go`):

| Tool | `args` string logged today | What's missing |
|---|---|---|
| `node_get` | `id=%q` | — (no filter argument; complete) |
| `node_grep` | `pattern=%q` | `filter` (a required part of the call when present) is never logged; **match count is never logged** |
| `subgraph_get` | `id=%q depth=%d` | `filter` is never logged; **node count in the returned patch is never logged** |
| `context_retrieve` | `query=%q filter=%t limit=%d` | `filter` is logged only as a boolean presence flag (`filter=true`/`filter=false`), never its actual content; **result node count is never logged** |
| `schema` | `""` (nothing) | not a filter/result-size gap — schema takes no input — but the response's predicate/class counts are not logged either |
| `node_match` | `""` (nothing) | **the entire call is logged with zero information** — not even the (required, non-optional) `filter` argument is captured; **matched-fact count is never logged** |

`node_match` is the sharpest case: unlike the other three filter-accepting tools, its `filter` argument is **required** (`nodeMatchArgs.Filter mcpFilter`, no `omitempty`) — every single call is filter-driven — yet `logCall("node_match", "", err)` logs an empty args string on both its call sites (`cmd/arc/graph/serve_tool_node_match.go:72,77`). An operator reading stderr cannot tell what any `node_match` call actually searched for.

This directly undercuts the stated purpose of the requirement that created `logCall` in the first place — **008-arc-serve-mcp spec.md FR-019**: *"For every tool call, the server MUST emit one line to stderr recording the tool name, its key arguments (id, pattern, or depth as applicable), and whether it succeeded or failed — sufficient for an operator to reconstruct what an agent asked for and what it got back, **without a separate metrics or tracing system**."* Two clauses of that sentence are not met by the current implementation:

- *"what an agent asked for"* — a filter is exactly the kind of argument that determines what an agent asked for, and it is silently dropped everywhere it exists.
- *"what it got back"* — nothing about the result (row/node/fact count) is captured at all; today's line only says `ok` or `error: <message>`, which satisfies "succeeded or failed" but not "what it got back."

Note also that FR-019 predates this feature (029) — filters on `subgraph_get`/`node_match` did not exist when FR-019 was written (they were added by later features: 027-triple-filter-model, 028-node-match-filter), so this gap is not implementation drift against FR-019's original scope; FR-019 has simply never been revisited as the tool surface grew a filter argument on four of its six tools. This feature (029) touched every one of these handler files for an unrelated reason (colocating each tool's metadata into its own `serve_tool_<name>.go` file) and would have been a natural place to also close this gap, but the metadata-colocation scope (spec.md's Stories 1-4) never asked for it.

## Artifact Traceability

### spec.md

- **Affected spec**: `specs/008-arc-serve-mcp/spec.md` (not the current feature's own spec — 029-mcp-tool-metadata's spec.md is entirely about tool/parameter *metadata* exposed to a connecting client, not about server-side operational logging; no requirement in 029's spec.md governs `logCall`).
- **Affected requirement**: **FR-019** — "the server MUST emit one line to stderr recording the tool name, its key arguments (id, pattern, or depth as applicable), and whether it succeeded or failed."
- **Gap identified**: FR-019's parenthetical ("id, pattern, or depth as applicable") was written before `filter` existed as an argument on any tool and was never updated when 027/028 added it to `subgraph_get`/`context_retrieve`/`node_match`; FR-019 also has no clause at all requiring that the *result* (count of items returned) be logged, despite its own stated goal of letting an operator "reconstruct ... what [the agent] got back." Additionally, FR-019 is silent on log format/technology (plain `fmt.Fprintf` vs. structured `log/slog`), which is now a concrete, named ask.

### plan.md

- **Affected plan**: `specs/008-arc-serve-mcp/plan.md` (original `logCall` design) — no corresponding section in 029-mcp-tool-metadata/plan.md, since 029's plan explicitly scoped `logCall` as an unchanged, cross-tool helper staying in `serve.go` ("Constraints" section: only `Description`/`InputSchema`/`Instructions` content changes; plan.md's Project Structure comment block for `serve.go` lists `logCall` as carried over, untouched).
- **Impact**: A fix would need a new plan (either a `specs/008-arc-serve-mcp` bugfix-patch, or its own small feature) documenting the `log/slog` + `github.com/fogfish/logger` dependency addition (a new Technical Context entry — this is a genuinely new external dependency, not yet in `go.mod`) and the revised per-call log-line shape (tool, args-including-filter, result count).

- **False completions**: none — every referenced task did what it asked at the time.
- **Missing tasks** (for `/speckit.bugfix.patch` or a new small feature to add):
  1. Add `github.com/fogfish/logger/v3` (already cached locally at v3.2.1; confirmed to be a real `log/slog` handler package — `logger.New(logger.Console...)` returns a `*slog.Logger` writing colored, single-line-per-record output to a terminal) to `go.mod`.
  2. Replace `logCall`'s `fmt.Fprintf`-based body with a package-level `*slog.Logger` (built once via `logger.New(logger.Console...)`) and structured `slog.Logger.Info`/`.Error` calls carrying `slog.String("tool", tool)`, the tool's own key arguments, and a new result-size argument — kept to one line per call (an explicit ask), e.g. via `slog`'s default single-line text/console format rather than multi-line JSON.
  3. Extend every handler's `logCall(...)` call site to (a) include a short, filter-aware summary (e.g. statement count, or the filter's compact JSON — not full pretty-printing) for `node_grep`/`subgraph_get`/`context_retrieve`/`node_match`, and (b) pass the count of returned elements (`len(result.Matches)` for `node_grep`/`node_match`, node count in the rendered patch for `subgraph_get`/`context_retrieve`, predicate+class counts for `schema`) — this requires moving each `logCall` invocation to *after* the domain call succeeds (today's success-path call already happens after the domain call returns, so this is available without restructuring control flow) while keeping the existing error-path call (which naturally has no result to count) unchanged in placement.
  4. Unit test(s) updating/extending `TestLogCallOutputShape` (`cmd/arc/graph/serve_test.go`) for the new structured line shape, plus new coverage asserting a filter's presence and a result count both appear in a successful call's log line for at least `node_grep` and `node_match` (the two clearest before/after cases: `node_grep` gains a previously entirely-absent filter, `node_match` goes from a fully empty args string to a fully populated one).

## Root Cause Analysis

FR-019 (008-arc-serve-mcp) was written and implemented (T025) when the server had no filter argument at all — `node_grep` and `subgraph_get`'s only "key arguments" were scalar (`pattern`, `id`, `depth`), so the parenthetical list and the plain-`fmt.Fprintf` implementation were both complete for the surface that existed at the time. Three later features (027-triple-filter-model, 028-node-match-filter, and this one's own predecessor tools) each added a `filter` argument to an existing or new tool, but none of them revisited FR-019's text or `logCall`'s call sites to keep the logging requirement's own stated goal ("reconstruct what an agent asked for and what it got back") true for the growing tool surface — each feature's own task list correctly scoped `logCall` as "no change needed" because logging wasn't that feature's concern. The result is a requirement that has silently drifted out of sync with the surface it was meant to describe, without any single feature's tasks ever being incorrectly marked complete. The additional ask (switch to `slog` + `github.com/fogfish/logger`, colored output) is a new, explicit technology preference layered on top of closing that same gap, not something any prior spec was expected to have anticipated.

## Recommended Fix

1. Run `/speckit.bugfix.patch` against **008-arc-serve-mcp** to amend FR-019 (drop the now-stale "id, pattern, or depth as applicable" parenthetical in favor of "the tool's key arguments, including a compact filter summary where the tool accepts one" and add an explicit result-size clause), and record the `log/slog` + `github.com/fogfish/logger` (colored console output) technology choice — plan.md/tasks.md updates per the "Missing tasks" list above.
2. Run `/speckit.bugfix.verify` to confirm consistency across the updated 008 spec artifacts.
