# Bug Report: `arc apply` rejects the host project's own markdown files

**Type**: Spec conflict
**Severity**: High
**Feature**: `031-init-existing-git-repo`
**Reported**: 2026-09-04
**Status**: Patched
**Patched**: 2026-09-04

## Description

After `arc init --skip-git-init` creates a graph at the **root** of an existing,
non-empty repository, every subsequent `arc apply` fails outright:

```
failed to write README.md: manifest is missing a mandatory field or uses the pre-0.5 node format: missing mandatory "@id" field
```

Reproduced end-to-end on `main` (commit `1fa3058`):

```sh
git init . && echo '# My Project' > README.md && git add -A && git commit -m initial
arc init --skip-git-init          # succeeds, graph layout created alongside README.md
arc apply tls13.patch.md          # exit 1, message above, nothing written, no commit
```

Three distinct defects compose into this failure:

1. **Whole-graph scan.** [apply.go:225](../../../internal/app/graph/service/apply.go#L225)
   calls `guardNoOldFormatNodes`, which walks *every* `*.md` file under the graph
   root ([apply.go:478-521](../../../internal/app/graph/service/apply.go#L478-L521))
   and attempts to parse each one as a graph node. At a root-mode graph, that
   walk reaches the host project's `README.md`, `CONTRIBUTING.md`, `docs/**.md`
   and so on — files `arc` does not own and must never interpret.

2. **The guard is obsolete.** It exists to detect the pre-0.5 node shape
   (spec 010 FR-012/FR-013). That format is retired and no longer produced by any
   `arc` version; the guard's only remaining effect is to turn every non-node
   markdown file in the tree into a hard failure. It converts a tolerable
   condition into a fatal one.

3. **The message names the wrong operation.** The guard is a read-path scan, but
   it wraps its rejections in `ErrNodeWrite` —
   `"failed to write %s"` ([errors.go:26](../../../internal/app/graph/service/errors.go#L26)).
   Nothing was written to `README.md`; nothing is ever written to it. The
   message misdirects the user toward a permissions or disk problem and
   violates FR-029's "actionable message" requirement.

The correct precedent already exists in this package: `Grep` performs the same
whole-graph walk but records unparseable files in an `Unreadable` list and
excludes them from the scan
([grep.go:100-107](../../../internal/app/graph/service/grep.go#L100-L107),
[kernel/grep.go:42-44](../../../internal/app/graph/kernel/grep.go#L42-L44)).
Under the same reproduction, `arc grep` succeeds silently. `apply` is the
outlier.

## Root Cause Analysis

**A premise changed and the requirement built on it was not revisited.**

When spec 010 wrote FR-012, `arc init` refused any non-empty target. The graph
root was, by construction, exclusively `arc`'s: every `*.md` beneath it was a
node `arc` had written. Under that premise, "walk the whole tree and reject the
first file that does not parse as a node" is a sound, cheap integrity check, and
`guardNoOldFormatNodes` implements it faithfully.

Spec 031 FR-010 deliberately removed that premise for `--skip-git-init` — the
whole point of the feature is that the graph now *shares* a directory with files
`arc` does not own. The guard's precondition was invalidated, but the guard was
never revisited, because 031's verification strategy (plan.md line 13,
research.md D7) framed the risk as **git-adapter scoping**: does the adapter
stage, query and resolve paths against the right repository? That framing is
correct and the adapter passed. It simply does not reach the filesystem-walk
layer, where the same "graph root is exclusively ours" assumption also lived
unstated.

The T013 fixture makes this concrete: `initHostGraph` puts unrelated content in
a *sibling* directory, which is the right fixture for testing repository
scoping and the wrong one for testing root sharing. Every US4 test passed
honestly; the scenario that fails was never written.

Two aggravating factors made the symptom worse than it needed to be:

- **The guard is dead weight.** It defends against a format no shipping version
  of `arc` produces. Its expected-value contribution is now zero, while its cost
  is a hard failure on every foreign markdown file. Deleting it is strictly
  better than narrowing it.
- **Error-type reuse across paths.** Borrowing `ErrNodeWrite` for a read-path
  scan produced a message that describes an operation the code never attempts.
  This is a small, local slip, but it is what made the failure hard to diagnose
  from the message alone — the reported symptom is a *write* failure on a file
  `arc` only ever read.

## Adjacent finding (not folded into this fix)

`arc lint` has the same whole-graph walk
([lint.go:207](../../../internal/app/lint/service/lint.go#L207)) and the same
broken premise. Under the identical reproduction it reports:

```
README.md:1 — [frontMatter] … missing mandatory "@id" field
1 nodes checked, 0 passing, 1 failing
```

It degrades gracefully (a reported violation, exit 0) rather than aborting, so
it is not a blocker — but it counts the host project's `README.md` as a failing
graph node, which contradicts 031 US4 Acceptance Scenario 4 and FR-025. This is
outside the fix the reporter scoped (`apply` only) and is recorded here so it is
not lost. It warrants its own decision: whether `lint` should skip non-node
markdown files silently, or list them the way `grep` lists `Unreadable`.

## Patch Record — 2026-09-04

Patched by `/speckit-bugfix-patch` with one scope directive from the reporter:
**`arc apply` must not scan the tree at all** (a performance requirement as
well as a correctness one), while **`arc lint` and `arc grep` maintain an
internal index of foreign unreadable files**. That directive promotes the
"Adjacent finding" above from *recorded but out of scope* to *in scope*: `lint`
is now covered by FR-035 alongside `grep`, and the open question it raised —
skip silently, or list them the way `grep` lists `Unreadable` — is answered in
favor of an internal index, consistent with `grep`'s existing shape.

One refinement to this report's own analysis, found while patching. The report
classified the conflict as spec 010 FR-012 versus spec 031 FR-010. Reading spec
010's User Story 3 acceptance scenarios more closely, all four are worded
**read-triggered** — "when any arc command **reads** it". FR-012 never asked
for a proactive whole-graph scan; `guardNoOldFormatNodes` over-implemented it.
The two readings were indistinguishable while `arc init` refused a non-empty
target, so this is not a defect in spec 010's wording. Spec 010 is therefore
annotated with a scope clarification rather than a strikethrough, and the
artifact-level conflict classification stands.
