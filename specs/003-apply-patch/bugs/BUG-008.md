# Bug Report: Case-variant node identities collide on case-insensitive filesystems — apply aborts with a misleading basename error on macOS/Windows, silently forks the graph on Linux

**Type**: Spec gap
**Severity**: High
**Feature**: 003-apply-patch (`arc apply`) — secondary traceability into 004-arc-lint and 022-reference-type-folders
**Reported**: 2026-09-02
**Status**: Resolved
**Patched**: 2026-09-02 — spec.md FR-026..FR-029 / SC-011 / SC-012, research.md D11, plan.md Technical Context, tasks.md T109-T117
**Resolved**: 2026-09-02 — see tasks.md T109-T117

## Description

An extraction pipeline emits the same entity under two spellings across two
documents: the first patch carries `LightStep`, the second carries
`Lightstep`. Applying the second patch on macOS (APFS, case-insensitive)
fails:

```text
[github.com/fogfish/arcnet-cli/internal/app/graph/service.readExistingNode 547]
failed to write Entity/Lightstep.md:
  "LightStep" does not match this file's basename "Lightstep"
```

The message is wrong twice over: no file is malformed, and the file it names
(`Entity/Lightstep.md`) does not exist. `rollback` leaves no partial write —
FR-015 holds, the graph is intact — but the operator is sent hunting for a
corrupt node file that isn't there.

The same input on a case-sensitive volume does not fail at all. It creates a
*second* node file, `Entity/Lightstep.md`, alongside `Entity/LightStep.md`,
silently forking one subject into two nodes.

Neither behaviour is specified. FR-005 ("identity does **not** already exist
→ create") and FR-006 ("identity **already** exists → merge") never define
what *existence* means against a filesystem that folds case, so the two
requirements select opposite branches on different volumes for byte-identical
input. The code faithfully implements the spec as written; the spec is silent.

### Reproduction

Confirmed with a two-patch fixture in `cmd/arc/graph` (temporary test, since
removed), built on the existing `tls13Patch` fixture and `initGraph` helper:

1. Apply patch A with entity id `LightStep` → creates `Entity/LightStep.md`.
2. Apply patch B (different `document` id) with entity id `Lightstep`.
3. Step 2 fails with the error above; exit non-zero, nothing committed.

Volume confirmed case-insensitive (`diskutil`, plus a `CaseTest.md` vs
`casetest.md` probe on the working volume).

### Platform split (today)

| Filesystem | Behaviour today | Assessment |
|---|---|---|
| Case-insensitive (APFS, NTFS, exFAT, many SMB mounts) | Apply aborts with a misleading basename-mismatch error; nothing written | Wrong error, no data loss |
| Case-sensitive (ext4, XFS, APFS case-sensitive volumes, CI) | `Open` returns `fs.ErrNotExist`; a second node file `Entity/Lightstep.md` is created alongside `Entity/LightStep.md` | Silently forks one subject into two nodes |

`checkUniqueBasenames`
([rules_frontmatter.go:24](../../../internal/app/lint/service/rules_frontmatter.go#L24))
keys on exact basenames, so the case-sensitive-volume outcome is never
reported by `arc lint` either.

## Root Cause Analysis

1. The target path is derived **purely from the incoming identity**. `nodePath`
   ([apply.go:57](../../../internal/app/graph/service/apply.go#L57)), called at
   [apply.go:304](../../../internal/app/graph/service/apply.go#L304), produces
   `Entity/Lightstep.md` — it consults nothing on disk.
2. `readExistingNode`
   ([apply.go:532](../../../internal/app/graph/service/apply.go#L532)) calls
   `store.Open("Entity/Lightstep.md")`. The local store's `Open`
   ([local.go:32](../../../internal/adapter/fsys/local.go#L32)) is
   `os.DirFS(root).Open`, i.e. the OS `open` syscall: on a case-insensitive
   volume that lookup **succeeds** and returns the bytes of the on-disk
   `Entity/LightStep.md`. The parsed node's `@id` is therefore `LightStep`.
3. `validateNodeBasename`
   ([apply.go:427](../../../internal/app/graph/service/apply.go#L427)) compares
   that parsed `@id` against `filepath.Base` of the **requested path string**,
   not the name the file actually carries on disk. `"LightStep" != "Lightstep"`
   → error raised at
   [apply.go:546](../../../internal/app/graph/service/apply.go#L546), whole
   apply aborted.

The guard is doing useful work. Without it, `os.Create`
([local.go:45](../../../internal/adapter/fsys/local.go#L45)) would truncate the
real `LightStep.md` **in place** — `os.Create` opens the case-folded match and
does not rename — leaving a file named `LightStep.md` whose merged content is
whichever `@id` won: genuine corruption that `arc lint` would then flag. The
defect is that the guard diagnoses a *filesystem-identity collision* as a
*malformed-file* error, and that no layer above it decides what a case-variant
identity actually means.

Note that `core.Merge` ([merge.go:63](../../../internal/core/merge.go#L63))
starts from `merged := existing`, so the existing node's `@id` always wins a
merge. The identity-folding half of the desired behaviour is already implicit
in the merge semantics; only the path resolution and the basename guard
disagree with it.

The repository already recognises this exact hazard class for **type folder**
names —
[folder-layout-contract.md C7](../../022-reference-type-folders/contracts/folder-layout-contract.md#L68-L72),
[022 plan.md:52](../../022-reference-type-folders/plan.md#L52),
[022 tasks.md:30](../../022-reference-type-folders/tasks.md#L30) ("never assert
a path with a filesystem stat; APFS is case-insensitive and would pass
`source/` for `Source/`"). Node **identities** were never given the same
treatment. That is precisely the gap.

## Required Behaviour (decided — carry into the patch phase)

**The tool MUST detect the host filesystem's actual case behaviour for the
graph root and react accordingly. It MUST NOT declare one global
identity-folding rule.**

### 1. Detect, do not assume

Case behaviour is a property of the mounted volume holding the graph, not of
the operating system: macOS can host case-sensitive APFS volumes, Linux can
mount exFAT/CIFS/`ext4 casefold` case-insensitively, and a graph may live on
an external or network volume that differs from the machine's boot volume.
Detection MUST therefore be a **runtime probe against the graph root itself**
(e.g. a throwaway file under the already-gitignored `.arc/`, stat'ed under a
flipped-case name), performed once per run and cached — never a `GOOS` build
tag or constant.

### 2. Case-sensitive filesystem → distinct identities

`LightStep` and `Lightstep` are two different nodes in two different files,
and identity comparison is exact. This is today's behaviour and it stays; it
becomes an intentional, documented outcome rather than an accident of `Open`
returning `fs.ErrNotExist`.

### 3. Case-insensitive filesystem → canonical behaviour

The identity already recorded on disk is canonical for that graph. An incoming
case variant MUST fold onto the existing node — merged into
`Entity/LightStep.md` under its existing `@id`, per the normal merge rules —
rather than aborting. The fold MUST be visible: a warning naming both the
incoming variant and the canonical identity it was folded into, surfaced in
`kernel.ApplyResult.Warnings` alongside the existing unrecognized-type warning
([apply.go:299](../../../internal/app/graph/service/apply.go#L299), FR-018's
precedent).

### 4. The diagnostic must stop lying

Whatever the filesystem, `validateNodeBasename` MUST compare a parsed `@id`
against the name the store reports for the file it **actually opened**, never
against a caller-constructed path string. Its genuine purpose — catching a
hand-edited node file whose `@id` drifted from its own filename — is preserved
by that change; the false positive is not. `guardNoOldFormatNodes`
([apply.go:445](../../../internal/app/graph/service/apply.go#L445)) already
walks real directory entries via `walkNodeFiles` and calls the guard with a
genuine on-disk path at
[apply.go:478](../../../internal/app/graph/service/apply.go#L478) — that call
site is a true positive and is unaffected.

> **Design constraint found while verifying this report.** "The name the store
> reports" is not obtainable from `Stat`. `fsys.Store`
> ([types.go:32-38](../../../internal/adapter/fsys/types.go#L32-L38)) is
> `fs.FS` + `fs.StatFS` + `fs.ReadDirFS` + `Create`/`Remove`, and the local
> store's `Stat` ([local.go:34](../../../internal/adapter/fsys/local.go#L34))
> delegates to `os` — whose `FileInfo.Name()` is derived from the **path string
> passed in**, not from the directory entry on disk. On a case-insensitive
> volume `Stat("Entity/Lightstep.md")` succeeds and reports `Name() ==
> "Lightstep.md"`. Only `ReadDir` on the parent folder yields the true on-disk
> spelling. Any fix for requirement 4 must therefore resolve the real name
> through `ReadDir` (or a store method that does), not through `Stat`.

## Explicit Non-Goal — no global canonical identity rule

Do **not** normalise identities graph-wide: no lowercasing, no case-folding on
read, no rewriting files to a canonical case. Node identities double as
wikilink targets (`[[LightStep]]`) consumed by third-party tools — Obsidian
above all — whose own link-resolution rules are outside this project's control
and are themselves case- and platform-dependent. Declaring a global canonical
form now would change what every existing `[[...]]` in every graph resolves to
in those tools, for a class of problem the filesystem only actually poses on
case-insensitive volumes. The behaviour stays scoped to what the filesystem
genuinely forces, and no further.

This is a **stated constraint**, not an open question. The patch phase must
record it as such.

## Open Questions for the Patch Phase

1. **Portability lint rule.** A graph authored on a case-sensitive volume with
   both `LightStep.md` and `Lightstep.md` cannot be checked out on macOS or
   Windows without a git collision. Should `arc lint` gain a case-insensitive
   basename-collision check — and is it a warning (portability advisory) or an
   error? Deliberately left undecided here; it belongs to 004-arc-lint's own
   rule set, not to this bugfix's minimum.
2. **Source-document idempotency.** The already-tracked check at
   [apply.go:245](../../../internal/app/graph/service/apply.go#L245) resolves
   `Source/<document>.md` through `vcs.IsTracked`
   ([git.go:138](../../../internal/adapter/git/git.go#L138)), i.e.
   `git ls-files --error-unmatch` — a **git path query**, not a filesystem one,
   with its own independent case semantics (`core.ignorecase`). Whether it
   folds case matters: two patches whose `document` ids differ only by case
   could otherwise both be ingested, defeating FR-014's idempotency guarantee
   on exactly the volumes where the node-level fold is meant to prevent
   duplication. **This must be verified empirically under
   `core.ignorecase=true` before the fix is designed, not assumed.**
3. **Pre-existing forked graphs.** If a graph already contains case-variant
   duplicates created on a case-sensitive volume and is then opened on macOS,
   what should `arc` do — report and refuse, or offer a repair path? Probably
   out of scope for this bugfix, but named here rather than left implicit.
4. **Probe failure.** If the probe cannot run (read-only mount, permission
   denied), which behaviour is the safe default? Suggested: treat the volume as
   **case-insensitive**, since that is the branch that refuses to fork the
   graph — it degrades to a merge plus a warning rather than to silent
   duplication.
