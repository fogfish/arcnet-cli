# Bug Report: git adapter issues repo-scoped commands for a graph-scoped port, silently corrupting `arc revert` when the graph is nested in a larger repository

**Type**: Spec gap (unstated graph-root == repo-root precondition), with an implementation-drift component on `ShowFile`
**Severity**: High — BUG 2 below breaks `arc revert`'s shared-node reconciliation outright (a hard error, no data loss) for any graph nested in a larger repository. ~~Critical — a silent wrong-answer path that makes `arc revert` compute and *commit* an incorrect reconciliation with no error surfaced to the user.~~ **Corrected 2026-09-03 during implementation** — see the BUG 2 section: the claimed silent-corruption path does not exist. The original assessment was not verified against real `git show` output before filing
**Feature**: 016-arc-revert (owns the `VCS` port contract covering 3 of the 4 affected calls) — cross-references 002-arc-init and 003-apply-patch (`StageAll`) and 004-arc-lint (`CommitsMatching`)
**Reported**: 2026-09-03
**Status**: Patched
**Patched**: 2026-09-03

## Description

`internal/adapter/git/git.go` runs every git subcommand as a subprocess with `cmd.Dir` set to the graph root (`run(ctx, dir, ...)`, `internal/adapter/git/git.go:271-287`). Four of those subcommands are **repo-scoped, not cwd-scoped**: git resolves them against the enclosing repository root and its full history, ignoring `cmd.Dir` for the purpose of scoping. They are therefore correct only in the one configuration every spec silently assumed — the graph root *is* the git repository root, which is what `arc init` produces (`internal/app/ctrl/service/init.go:85`, `vcs.Init(ctx, dir)`).

Nothing enforces that configuration. Every command resolves its root as `filepath.Abs(".")` (`cmd/arc/graph/apply.go:121`, `cmd/arc/graph/grep.go:265`, `cmd/arc/graph/serve.go:368`) and the only "is this a graph" test anywhere is `store.Stat(".arc")`. A user who `git init`s a parent directory above their graph, keeps a graph inside an existing repository, or adopts a future multiple-graphs-per-repository layout gets all four defects with no warning.

All four were verified empirically against a real repository containing two sibling subdirectories `a/` and `b/`.

### BUG 2 — `ShowFile` resolves the path against the repo root, failing every historical read (`git.go:265`)

Listed first because it is the most disruptive.

`git show <hash>:<path>` resolves `<path>` **relative to the repository root**, not to `cmd.Dir`. Run from `a/`:

```text
$ git show HEAD:f.md
fatal: path 'a/f.md' exists, but not 'f.md'
hint: Did you mean 'HEAD:a/f.md' aka 'HEAD:./f.md'?

$ git show HEAD:./f.md
one
```

So in a nested graph **every** `ShowFile` call fails. The consumers are `resolveConflictMarker` (`internal/app/graph/service/revert.go:496`) and `reconcileShared`, which walk a node's history oldest-first via `ShowFile` + `core.ParseNode` to establish a predicate's true first writer (the D8(b) algorithm). Both propagate the error (`return "", false, err`), so `arc revert` aborts on any node whose reconciliation needs a historical read — FR-012/FR-013's whole merge-aware path is unusable for a nested graph.

Fix: request `<hash>:./<path>` so git resolves the path relative to `cmd.Dir`.

> **Correction (2026-09-03, during implementation).** This report originally claimed the resolution fatal is swallowed and returned as `(nil, nil)`, silently corrupting reconciliation. **That is wrong**, and the severity above is corrected from Critical to High. Verified against real `git show` output, the three relevant messages are:
>
> | Condition | Message | Matches a marker? |
> |---|---|---|
> | Path resolved against repo root | `fatal: path 'a/f.md' exists, but not 'f.md'` | **No** |
> | Absent at commit, absent on disk | `fatal: path 'a/nope.md' does not exist in 'HEAD'` | Yes — `does not exist in` |
> | Absent at commit, present on disk | `fatal: path 'a/new.md' exists on disk, but not in 'HEAD'` | Yes — `exists on disk, but not in` |
>
> The resolution fatal matches **neither** entry of `showFileMissingMarkers`, so it falls through to `return nil, ErrGitShow.With(err)` — a visible error, exactly as the contract intends. `showFileMissingMarkers` is correct as written and needs no change; the marker-narrowing work originally proposed here is dropped as unfounded. What remains is the genuine defect: the missing `./` prefix.

### BUG 1 — `StageAll` stages the entire repository (`git.go:107`)

`git add -A` with no pathspec operates on the **whole tree**, not on `cmd.Dir`, since git 2.0. Reproduction — with `a/` and `b/` both dirty, run from `a/`:

```text
$ git add -A
$ git diff --cached --name-only
a/f.md
b/dirty.md
```

Consequence: `arc apply` (`internal/app/graph/service/apply.go:422`) and `arc revert` (`internal/app/graph/service/revert.go:132`) sweep unrelated files from anywhere in the repository into the graph's ingest or revert commit. The commit stops being an accurate record of one document's contribution, which is the invariant everything downstream reads back out of history.

Fix: `git add -A -- .`

### BUG 3 — `ChangedPaths` returns repo-root-relative paths spanning every graph (`git.go:180`)

`git diff-tree --no-commit-id --name-only -r --root <hash>` emits paths relative to the **repository root** and includes everything the commit touched. Run from `a/`:

```text
$ git diff-tree --no-commit-id --name-only -r --root $H
a/f.md
b/f.md

$ git diff-tree --no-commit-id --name-only -r --root --relative $H
f.md
```

Consequence: `service.Revert` (`internal/app/graph/service/revert.go:87`) treats each returned path as graph-root-relative and passes it to `store.Stat` and `CommitsTouching`. Paths either fail to resolve (`a/f.md` looked up inside the graph rooted at `a/`) or leak in from outside the graph entirely.

Fix: add `--relative`, which both rebases the output onto `cmd.Dir` and filters out everything above it.

### BUG 4 — `CommitsMatching` searches the whole repository history (`git.go:161`)

`git log --all --fixed-strings --grep=<needle> --format=%H` carries no pathspec, so it matches commits belonging to any graph in the repository.

Consequence: `arc revert`'s ingest-commit lookup (`internal/app/graph/service/revert.go:52`) and lint's FR-010 one-ingest-commit-per-document check (`internal/app/lint/service/rules_history.go:28`) both match foreign commits. Two graphs in one repository that ingested the same citekey produce a wrong ingest-commit resolution — and since BUG-001's fix made `Revert` act on `hashes[0]` unconditionally rather than refusing on multiplicity, the failure is now silent selection of another graph's commit rather than a visible refusal.

Fix: append a `-- .` pathspec. Verified to still return the expected commit when scoped.

### plan.md

- **Affected sections**: `specs/016-arc-revert/plan.md`'s Project Structure entry for `internal/adapter/git/git.go` ("shared git adapter") and its Technical Context, neither of which records a repository-topology precondition for the adapter.

  - Line 29 specifies `git diff-tree --no-commit-id --name-only -r <hash>` with no `--relative` (BUG 3).
  - Line 33 specifies `git show <hash>:<path>` with no `./` (BUG 2) — and, in the same cell, *prescribes* the marker-matching approach that turns BUG 2 from a visible failure into a silent one: "implemented by checking `git show`'s specific 'does not exist' exit condition the same way `IsTracked` already distinguishes an expected 'not tracked' exit from a genuine failure." The analogy to `IsTracked` does not hold: `IsTracked` discriminates on a numeric **exit code** (1), which is unambiguous; `ShowFile` was left discriminating on **message substrings**, which are not.
  - Line 28 specifies `git log --all --fixed-strings --grep=<needle> --format=%H` with no pathspec (BUG 4), and explicitly notes it was "reused verbatim" from 004-arc-lint — carrying the defect forward without re-examination.

- **Impact**: the contract's command mapping needs a fifth column or a per-row note recording *scope*, plus a new invariant stating that every command MUST be scoped to `dir`'s subtree, with the mechanism named per command (pathspec, `--relative`, or `./` path prefix). The `ShowFile` row's `IsTracked` analogy needs correcting.

## Root Cause Analysis

A single unstated precondition, inherited across four features.

`arc init` creates the graph and the repository together in one directory (`internal/app/ctrl/service/init.go:85`), so during 002-arc-init's development the graph root and the repository root were the same path in every test and every manual run. `StageAll` was specified as "`git add -A` in `dir`" — accurate for that topology, and the distinction between "runs with cwd = dir" and "is scoped to dir" never had to be drawn because the two coincided.

003-apply-patch reused the port verbatim. 004-arc-lint added `CommitsMatching` under the same assumption. 016-arc-revert then added five more history-reading commands and — per its own contract, line 28 — reused `CommitsMatching` "verbatim," inheriting the assumption a fourth time without re-examining it. At no point did a feature own the question, because at no point did a feature *introduce* the coupling; it was always already there.

~~The `ShowFile` marker heuristic (BUG 2) is a distinct and more serious failure...~~ — **withdrawn (2026-09-03, during implementation)**: verified against real `git show` output, the two markers match only the two genuine absence conditions and never the path-resolution fatal, so there is no drift and no silent misread. `ShowFile`'s only defect is the shared one — the missing `./` scoping prefix. Substring matching over git's human-readable diagnostics remains fragile in principle (an exit-code discriminator would be sturdier), but that is a hardening preference, not a defect, and is deliberately not part of this fix.

The four defects are independent of, and prerequisite to, any decision about hosting multiple graphs per repository. They should be fixed regardless: BUG 2 can silently corrupt `arc revert` output **today** for any user whose graph happens to sit inside a parent repository — a configuration nothing in the tool detects, warns about, or prevents.

One follow-up remains open as T052: no test outside the git adapter exercises `ShowFile` against real git, a pre-existing gap this work surfaced.

**Decide before patching**: whether a nested graph is *supported* (fix all four calls to be subtree-scoped, which this report assumes) or *rejected* (detect at mount that the graph root is not the repository root and refuse). Subtree-scoping is the better answer — it is four one-line changes, it makes the FR wording "the graph's git history" literally true, and it costs nothing in the repo-root case — but it is a product decision that belongs in the spec, not in the adapter.

**Correction taken (2026-09-03, implementation)**: BUG 2's severity is corrected from Critical to High and its silent-corruption claim withdrawn (see the BUG 2 section). The four defects and their fixes are otherwise unchanged; all four remain real, and BUG 2 still makes the merge-aware revert path unusable for a nested graph.

**Decision taken (2026-09-03, bugfix patch)**: **subtree-scoping** — a graph MAY be nested inside a larger repository, and every history operation is explicitly confined to the graph directory. Recorded as spec.md **FR-021**, SC-010, a new Edge Case, and a corrected Assumption, with the per-command mechanism recorded as invariant 4 of contracts/vcs-port-contract.md. Note what this decision does *not* do: it makes the four git calls correct, but it does not by itself deliver multiple-graphs-per-repository as a product capability (that additionally needs an `arc init` that can skip repository creation, and a root-resolution story better than each command's current `filepath.Abs(".")`). Those remain out of scope here — this patch fixes defects that are live today for any single graph that happens to sit inside a parent repository.
