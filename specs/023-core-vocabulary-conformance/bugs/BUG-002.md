# Bug Report: `notes` and `relevance` are still registered, seeded, and used as Reference's leading predicate — CORE's current worked examples retire both outright

**Type**: Spec conflict (upstream CORE spec's own §11.6 worked example has moved past what spec 023's BUG-001 implementation read from it — the same class of drift BUG-001 itself was filed to close, now recurring for two predicates BUG-001's own round of fixes didn't catch)
**Severity**: High
**Feature**: 023-core-vocabulary-conformance (FR-028, FR-033, `internal/app/schema/kernel/schema.go`'s `CorePredicateDefs`/`CoreTypeDefs`); also touches 010-predicate-node-model (`internal/core.textPredicateFor`'s trailing-slot design) and 024-lint-conformance-gaps (the `typeOptional` rule this bug's `notes` symptom was first reported against, spec 010 BUG-005)
**Reported**: 2026-09-05
**Status**: Resolved
**Patched**: 2026-09-05 — see spec.md FR-028 (corrected), FR-038 (added), FR-033 (annotated), tasks.md Phase 11 (T074-T080), plan.md F7 row corrected. Companion to spec 010 BUG-007; the two land together.
**Resolved (implementation)**: 2026-09-05 — `"notes"`/`"relevance"` removed from `CorePredicateDefs`; `Reference`'s `CoreTypeDefs.Optional` drops `"relevance"`, gains `"text"`. Golden schema snapshot regenerated (two `_schema/Property/` documents deleted, `Class/Reference.md` updated). `TestSeedRetiredPredicatesAreGoneEntirely`'s exhaustive absence check now includes both names. Full module-wide sweep of test fixtures referencing either name by literal string, landed in the same pass as spec 010's own BUG-007 implementation (`textPredicateFor`'s trailing-slot collapse) since the two are inseparable — vocabulary retirement alone would have left `Reference`'s prose with nowhere correct to go. `go build`, `go vet`, `go test ./...` all pass clean; `staticcheck` unavailable (pre-existing local toolchain mismatch, unrelated). Manually re-verified via a real `arc init`/`arc apply`/`arc lint` run and a full-tree grep of the written graph: neither `notes` nor `relevance` appears anywhere.

## Description

While verifying spec 010's BUG-005 fix (a `**Label**`-headed prose block resolving to its own predicate instead of the type-blind `notes` catch-all), the user pointed out that `arc lint` still treats *any* unlabeled trailing prose on an `Entity`/`Resource` node as the `notes` predicate — and that `notes` "MUST BE removed from everywhere," not merely tolerated as a known lint failure.

Checking the currently-installed `ARCNET-CORE.md` (Version 0.12, 2026-08-23 — the exact revision spec 023's own BUG-001 targeted) confirms this is correct, and broader than reported: **`relevance` is retired too**, in the very same upstream revision note BUG-001 already read once:

> `notes` (`Entity`, `Resource`), `ref` and `status` (`Reference`'s worked example), `granularity` (`Timeline`'s worked example), and **`relevance` (mentioned only in prose, never actually registered or required)** are all retired outright — none were `_schema/Property/` nodes and none are reinstated.

And `Reference`'s own current worked example (§11.6) confirms both are gone from its Optional list, which now reads exactly:

```markdown
## Optional
- optional:: [[url]]
- optional:: [[author]]
- optional:: [[published]]
- optional:: [[doi]]
- optional:: [[isCitedBy]]
```

No `notes`, no `relevance` — a change from the 0.9→0.10 revision, which had given `Reference` "optional `url`/`authors`/`year`/`doi`/`status`/`isCitedBy`/`notes`" (i.e. `Reference` briefly *did* own `notes`, which is presumably why spec 023's BUG-001 kept it registered "because Reference still declares it" — a decision that was current for 0.10/0.11 but is stale against 0.12).

This codebase still:

- registers `notes` and `relevance` as real predicates (`internal/app/schema/kernel/schema.go:93,102`)
- keeps `relevance` in `Reference`'s `CoreTypeDefs.Optional` (`internal/app/schema/kernel/schema.go:203`)
- hardcodes `textPredicateFor`'s trailing-slot key to the literal string `"notes"` for every type except `Reference`, and `relevance` as `Reference`'s own leading key (`internal/core/markdown.go:436-460`), with a duplicate copy of this same logic in `revertLeadingKey` (`internal/app/graph/service/revert.go:404-436`)
- ships golden schema fixtures for both (`internal/app/schema/service/testdata/golden/schema/_schema/Property/{notes,relevance}.md`, `.../Class/Reference.md`)

CORE's actual model has no "trailing catch-all" text predicate concept at all: §5's own rule is "start with values from default `text` predicate and continue into other `text`-role predicates" — exactly one anonymous leading predicate per type, plus any number of explicitly *named* ones. There is no second, unlabeled, always-present slot for content that happens to appear later in the document.

### research.md / spec 010 cross-reference (architectural note, not this feature's own FR)

`internal/core.textPredicateFor`'s `!leading` branch (the literal `return "notes"` at `internal/core/markdown.go:438`) is spec 010's own design, not spec 023's — but its continued existence is precisely what makes this vocabulary gap user-visible as a lint failure (spec 010 BUG-005's own T068-adjacent finding) rather than a purely internal naming inconsistency. Retiring `notes` from the *vocabulary* (this bug, spec 023) without also retiring the *trailing-slot concept* that names itself after it (spec 010) would just swap the hardcoded literal for a different, still-nonexistent-in-CORE predicate name and reproduce the identical symptom under a new name. CORE's own model — "one default `text` predicate, plus any number of explicitly named ones, no second unlabeled slot" — has no trailing/leading distinction at all; `walkNodeBody`'s trailing accumulator should merge into the *same* leading key (`texts[textPredicateFor(nodeType)]`, appended) rather than a structurally separate key. This is flagged here for cross-reference; the actual FR/task changes for `internal/core`'s parser/renderer belong in spec 010's own bugfix-patch pass, run alongside this one so the two land together (a partial fix — vocabulary retired here, trailing-slot design untouched there, or vice versa — would leave the graph in a state neither spec fully describes).

## Root Cause Analysis

Spec 023's BUG-001 (2026-08-23) correctly identified that CORE's upstream spec had moved from 0.10/0.11 to 0.12 and re-synced this codebase's seeded vocabulary against the seven predicates its own program brief had already catalogued as drifted (`definition`→`text`, `authors`→`author`, `year`→`published`, `notes`/`ref`/`status`/`granularity` retired). The *same* 0.11→0.12 revision note that lists those seven also separately retires an eighth item — `relevance` — in a trailing clause ("and `relevance` (mentioned only in prose, never actually registered or required) are all retired outright") that BUG-001's own investigation did not carry into its FR-030–FR-037 sweep, because `relevance` was never one of the seven names the pre-existing program brief had flagged going in. `notes` fared partially better — BUG-001 did retire it from `Entity`/`Resource` (FR-033) — but kept it registered "because Reference still declares it," a decision correct against the 0.9→0.10-era worked example BUG-001's own comment cites, and never re-checked against `Reference`'s *current* (0.12) worked example, which had already dropped it by the time BUG-001 landed.
