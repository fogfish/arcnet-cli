# Bug Report: `textPredicateFor`'s hardcoded trailing-slot key has no counterpart in ARCNET-CORE's actual model — CORE has one primary `text`-role predicate per type plus any number of explicitly named ones, never a second unlabeled slot

**Type**: Spec gap (research.md D4 flagged the two-slot leading/trailing design as "a temporary stopgap" from spec 010's own original implementation, superseded in name only by later bugfixes — the structural assumption itself was never revisited)
**Severity**: High
**Feature**: 010-predicate-node-model (`internal/core.textPredicateFor`/`walkNodeBody`/`renderNodeBody`'s leading/trailing two-slot design); companion to 023-core-vocabulary-conformance's [BUG-002](../../023-core-vocabulary-conformance/bugs/BUG-002.md), which retires the vocabulary name (`notes`) this bug's trailing slot renders under — the two MUST land together
**Reported**: 2026-09-05
**Status**: Resolved
**Patched**: 2026-09-05 — see spec.md FR-026, tasks.md Phase 11 (T117-T121). Companion to spec 023 BUG-002; the two land together.
**Resolved (implementation)**: 2026-09-05 — `textPredicateFor` collapsed to `func textPredicateFor(nodeType string) string` (one key per type); `walkNodeBody` merges trailing-scan text into the same key as leading (blank-line-joined); `renderNodeBody` writes it once, in the leading position, with no separate trailing-key write. `internal/app/graph/service/revert.go`'s duplicate (`revertLeadingKey`, `physicalTextKeyOrder`, `mapTextParagraphs`) updated identically; the module-level `revertTrailingKey = "notes"` constant deleted. **Implementation finding beyond the original plan**: merging leading and trailing prose into one physical render position exposed a real, previously-latent round-trip bug — two separate untitled bare lists, no longer separated by the intervening Edges block, can end up string-adjacent with only a blank line between them, and CommonMark silently merges same-marker bullet lists across a blank line into one loose List node (verified directly against goldmark's own AST), losing the boundary on the next parse and breaking FR-015. Fixed by alternating the bullet marker (`"*"`/`"+"`) every time an untitled list renders into the merged value (`nextBareList`); `renderBareTextListLines` (now dead) was deleted in favor of calling `renderMarkedListLines` directly. See plan.md's Complexity Tracking for the full analysis. Verified via new tests (`TestParsePatchLeadingAndTrailingProseMergeIntoOneKey`, `TestRoundTripLeadingAndTrailingProseIdempotent`) and a manual `arc init`/`arc apply`/`arc lint` run confirming the merge and its correct render position. `go build`, `go vet`, `go test ./...` all pass clean; `staticcheck` unavailable (pre-existing local toolchain mismatch, unrelated).

## Description

`internal/core.textPredicateFor(nodeType string, leading bool) string` returns a *different* predicate name depending on whether the caller asks for the "leading" or "trailing" prose position:

```go
func textPredicateFor(nodeType string, leading bool) string {
	if !leading {
		return "notes"
	}
	switch nodeType {
	case "Source":
		return "abstract"
	...
	}
}
```

`walkNodeBody` accumulates every unlabeled paragraph occurring *before* the first list/titled block into `leading`, and every unlabeled paragraph occurring *after* into `trailing` — then stores them under two structurally different keys (`texts[textPredicateFor(type, true)]` and `texts[textPredicateFor(type, false)]`). `renderNodeBody` writes them back in two different body positions: the leading key first, the trailing key dead last, after every edge and link-role block.

ARCNET-CORE's actual model has no such second slot. §5 states the rule plainly: "Start with values from default `text` predicate and continue into other `text`-role predicates" — exactly one anonymous, default-named `text`-role predicate per type, rendered first, plus any number of *explicitly named* ones (each with its own `**Label**`). There is no third category for "unlabeled prose that happens to appear later in the document." A document with prose both before and after its edge/link content should therefore parse to **one** `text`/`abstract`-keyed value (the two prose spans concatenated), not two differently-named values — one of which spec 023's own BUG-002 shows doesn't even correspond to a real, currently-registered predicate.

## Artifact Traceability

### spec.md (010-predicate-node-model)

- **Affected requirements**:
  - **FR-005**: "Arc MUST support an open, unbounded set of named prose fields per node" — the trailing slot is not a *named* field in CORE's sense; it is a structural accident of where content happened to sit in the source document, given an unconditional, type-blind name.
  - **FR-006**: "Arc MUST preserve each prose field's content verbatim under its own name" — currently satisfied only in the narrow sense that a fixed literal string is used consistently; the deeper requirement (that the *name* correspond to a real predicate) fails whenever the trailing slot's hardcoded name isn't one, which is now demonstrably the case (spec 023 BUG-002).
- **Gap identified**: research.md D4 (spec 010's own original design note) already flagged the two-slot leading/trailing split as "a temporary stopgap ... pending spec 011's Schema Index." Spec 011 shipped; spec 013 wired schema roles into rendering; spec 010's own BUG-002/003/004/005/006 each extended the *titled*-block half of the parser considerably — but the *un*titled leading-vs-trailing structural split itself was never revisited. It is the one piece of the original stopgap that outlived every reason it was introduced for.
- **Missing FR**: a new requirement stating that a type has exactly one default (unlabeled) `text`-role predicate, and any unlabeled prose — regardless of its position relative to edges, links, or titled blocks in the source document — contributes to that single predicate's value, never to a second, differently-named one.

### tasks.md (010-predicate-node-model)

- **Affected tasks**: T024 (original leading/trailing recognition, spec 010 Phase 2.5) and every later task built on top of it (T086/T101/T102/BUG-004's resumable pairing) correctly preserved the two-slot *shape* through each successive bugfix without ever being asked to question whether the shape itself was still correct once spec 011/013 existed. None of these are false completions — the shape was explicitly in scope for each — but the shape itself is now the defect.
- **Missing tasks**:
  1. Collapse `textPredicateFor`'s two-argument signature (`leading bool`) to a single-value form, `func textPredicateFor(nodeType string) string` — one key per type, matching CORE's one-default-predicate-per-type model. `internal/core/markdown.go:436-460`.
  2. In `walkNodeBody` (`internal/core/markdown.go`), merge `trailing`'s accumulated raw text into the *same* key as `leading`'s (append, blank-line-separated) instead of writing it under `textPredicateFor(nodeType, false)`. The parser's existing leading/trailing *positional scanning* (which content is "before" vs "after" titled blocks) is unchanged — only the *key* the trailing scan's result is stored under changes.
  3. In `renderNodeBody` (`internal/core/markdown.go`), remove the separate trailing-key write entirely; the single merged primary-key value renders once, in the existing leading position (before every other named text-role predicate and every edge/link block) — matching CORE §5's canonical ordering, which never places the default `text` predicate after edges.
  4. Update `revertLeadingKey`'s duplicate copy (`internal/app/graph/service/revert.go:404-436`) identically, preserving the documented invariant that the two functions must always agree.
  5. Regression tests: (a) a node with unlabeled prose both before and after a titled/edge block round-trips to one merged value under the type's single default key, not two; (b) round-trip and idempotent round-trip stability for this merged shape (FR-014/FR-015); (c) a pre-existing fixture that previously exercised the trailing slot (search `internal/core/markdown_test.go` for any test asserting `Texts["notes"]`/`Texts["relevance"]` as a value distinct from the leading key) is updated to expect the merged value instead.
  6. Land this change in the *same* implementation pass as spec 023's [BUG-002](../../023-core-vocabulary-conformance/bugs/BUG-002.md) — retiring the `notes`/`relevance` vocabulary names without also retiring the structural slot that names itself after them (or vice versa) leaves the graph in a state neither spec fully describes.

## Root Cause Analysis

`walkNodeBody`'s leading/trailing split predates this codebase's schema-role machinery entirely — it is a direct carryover from the pre-spec-010 two-fixed-field (`Text`/`Notes`) representation research.md D4 explicitly named as a stopgap when it introduced the open-keyed `Texts` map. Every bugfix since (BUG-002 through BUG-006) extended what happens once a `**Label**`-headed *titled* block is recognized, correctly treating that as CORE's real predicate-naming mechanism — but none of them asked whether the *un*titled leading/trailing split, sitting right alongside the titled-block logic the whole time, was itself still a legitimate CORE concept. It never was one; it was always an implementation detail of the old two-field model, given new names (`textPredicateFor`'s per-type switch) but never a new *shape*.
