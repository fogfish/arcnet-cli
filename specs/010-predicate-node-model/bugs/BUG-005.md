# Bug Report: `classifyNodeBody`'s title+list-only pairing swallows a `**Label**`-headed *prose* block into the hardcoded trailing "notes" slot — lint rejects it, and it renders after edge/link blocks instead of in its own place

**Type**: Spec gap (FR-019/FR-023's title+list pairing was never extended to title+prose, the shape a `text`-role predicate's own body block actually takes per ARCNET-CORE §5); compounded by a previously-documented, deliberately deferred gap in spec 023 BUG-001 (T068)
**Severity**: High
**Feature**: 010-predicate-node-model (`classifyNodeBody`/`walkNodeBody`, FR-005/FR-006/FR-019); also touches 013-predicate-role-rendering (render-shape-contract.md step 6) and 023-core-vocabulary-conformance (BUG-001's T068 deviation, the retirement of `notes` for `Entity`/`Resource`)
**Reported**: 2026-09-05
**Status**: Resolved
**Patched**: 2026-09-05 — spec.md gained an Edge Cases entry and FR-024 (title+paragraph pairing, mirroring FR-019/FR-023's title+list pairing), plus a closing Bugfix note. plan.md gained a Constraints reopen note, a corrected Complexity Tracking row (BUG-003's row wrongly claimed "the deferral is now resolved" for this exact paragraph-pairing gap — struck and corrected), and a new Complexity Tracking row for BUG-005. tasks.md reopened T089 (false completion — its own description named the "plain prose" sub-case, never actually tested) and added Phase 9 (T106-T111). specs/013's contracts/render-shape-contract.md gained a clarifying note on step 6, confirming no rendering-order code change is needed once the parse-side gap is fixed. No change made to spec 023 — BUG-001's T068 residual (unlabeled trailing prose on `Entity`/`Resource`) stays open and untouched by this patch (see T109).
**Resolved (implementation)**: 2026-09-05 — `/speckit-implement` landed Phase 9 (T106-T111). The root cause turned out one layer deeper than this report's own analysis: CommonMark joins `**Label**` and an immediately following line of prose (no blank line between them) into a *single* goldmark `Paragraph` node via a soft line break — there is no second AST sibling for a "pair title with following sibling" check to ever find, which is exactly the shape the reported reproduction uses. `internal/core/markdown.go` gained `splitLeadingBoldLabel` (recognizes a paragraph whose first raw source line alone is a complete `**Label**` run) and `collectTitledProse` (absorbs further plain paragraphs as continuation content, stopping at a child that is itself title-shaped via either `blockTitle` or `splitLeadingBoldLabel` — closing an adjacent-titles-with-no-content-between edge case discovered while testing); `bodyBlock` gained a `content []string` field, and `walkNodeBody` routes it through a new `namedTextParas` map into `extractInlineLinks`/`reconstructHRefs` (CORE §5's `href` role for genuine prose), parallel to the pre-existing list-sourced `namedTexts`/`renderTextListLines` path (FR-020 governs list items, not paragraphs). T106/T107's task descriptions were corrected in tasks.md to reflect this — the original plan (extend title+list sibling-pairing to also accept a paragraph sibling) was necessary but not sufficient for the bug's own literal reproduction. Verified via new unit tests (`internal/core/markdown_test.go`, `internal/app/lint/service/rules_type_conformance_test.go`) and a manual `arc init`/`arc apply`/`arc lint` run against the exact reported reproduction: `Overview` now resolves to its own `overview` predicate, renders before the edge list and `## Concerns`, and passes `arc lint` once `Entity`'s schema records `overview` as Optional — the same one-time step any newly auto-registered predicate already requires (confirmed symmetric with `concerns`/`derivedFrom` in the same run). `go build ./...`, `go vet ./...`, and `go test ./...` all pass clean; `staticcheck ./...` could not run due to a pre-existing local toolchain/staticcheck-version mismatch unrelated to this change.

## Description

A patch node body containing a `**Label**`\-headed block whose content is a **prose paragraph** (not a list) —

```markdown
**Overview**
Overview text
```

— is silently misclassified. `arc apply` accepts the patch, but the written node fails `arc lint` with:

```
[typeOptional] predicate "notes" is not permitted by type "..." (not listed under its Requires or Optional)
```

and, independent of the lint failure, the block also renders in the wrong position: after every edge/link block, instead of alongside the node's other named text-role predicates (before the edges), and with its own `**Overview**` label baked into the prose as literal text rather than reappearing as a heading/bold-label on write.

**Reproduction** (verified directly against `internal/core.ParsePatch`/`RenderNode`, `index` declaring `derivedFrom: edge`, `concerns: link`):

Input body (patch):
```markdown
*important text*

- derivedFrom:: [[document]]

**Overview**
Overview text

**Concerns**
- concerns:: [[A]]
- concerns:: [[B]]
```

Parses to:
```go
Texts: {"text": "*important text*", "notes": "**Overview** Overview text"}
Edges: [derivedFrom→document, concerns→A, concerns→B]
```

`"notes"` — not `"overview"` — carries the block's content, and the literal `**Overview**` label text is embedded inside the prose value rather than being recognized as a label at all.

Re-rendering that `Node` via `RenderNode` reproduces the user's exact `<node-in-graph>` shape byte-for-byte:
```markdown
# Title

*important text*

- derivedFrom:: [[document]]

## Concerns
- concerns:: [[A]]
- concerns:: [[B]]

**Overview** Overview text
```

`**Overview**`/"Overview text" ends up on one line, after `## Concerns`, and under the predicate name `notes` — which CORE 0.12 retired from `Entity`/`Resource`'s Optional list (spec 023 FR-033), so `arc lint`'s `typeOptional` rule (`internal/app/lint/kernel/lint.go`, `RuleTypeOptional`) correctly rejects it.

## Artifact Traceability

### spec.md (010-predicate-node-model)

- **Affected user story**: User Story 1, Acceptance Scenario 2 — "a node file with several independently named prose sections (e.g. `abstract`, `relevance`) … every prose section is preserved individually, under its own name."
- **Affected requirements — currently violated**:
  - **FR-005**: "Arc MUST support an open, unbounded set of named prose fields per node" — a `**Label**`-headed prose block never becomes a named field at all; it is absorbed into the fixed `notes`/leading-slot key.
  - **FR-006**: "Arc MUST preserve each prose field's content verbatim under its own name" — `Overview`'s content is preserved as *bytes*, but not under its own name, and its label text is folded into the prose value instead of being dropped/reconstructed as a heading.
  - **FR-019**: "a `**Label**`-prefixed body block (list **or paragraph**) MUST have its predicate identity resolved against the graph's schema index … The resolved predicate's declared role … MUST determine whether its content is captured as a link … or as prose under that predicate's own name." FR-019's own text already covers the paragraph case explicitly ("list or paragraph") — the implementation does not.
  - **FR-021**: a predicate auto-registered from a `**Label**`-headed block must recover its original label on write — moot here, because no predicate is ever auto-registered for this block in the first place.
- **Gap identified**: `classifyNodeBody` (`internal/core/markdown.go:749`) pairs a title (`blockTitle`, matching either `"## Label"` or `"**Label**"`) with the following sibling **only when that sibling is an `*ast.List`** (`internal/core/markdown.go:761-765`: `if list, ok := children[idx+1].(*ast.List); ok`). When the title is instead followed by an `*ast.Paragraph`, no `bodyBlockTitled` is produced at all — both the title paragraph and the following prose paragraph fall through to `bodyBlockProse` individually (`internal/core/markdown.go:766-770`), indistinguishable from ordinary untitled prose, and both are then swept into whichever of `walkNodeBody`'s leading/trailing catch-all slots they happen to land in positionally (`internal/core/markdown.go:827-903`). `resolveLabelPredicate` (`internal/core/markdown.go:998`) — the schema-role lookup FR-019 requires — is only ever invoked from the `bodyBlockTitled` case (`internal/core/markdown.go:850`), so it is never reached for a title+prose pairing; the label is never resolved, never auto-registered, and never treated as anything but literal prose text.

### spec.md / bugs (023-core-vocabulary-conformance)

- **Affected section**: BUG-001's own "Resolved (implementation)" note documents a **known, deliberate, still-open deviation**: *"(T068) `textPredicateFor`'s non-leading-prose branch was left type-unaware — no safe replacement key exists for Entity/Resource's trailing prose, so the schema-table removal alone (which makes lint correctly flag any use) was judged sufficient."* This bug's lint symptom (`typeOptional`: `"notes"` not permitted) is exactly the behavior T068 predicted and accepted as an interim state for *any* trailing prose on an `Entity`/`Resource` node that doesn't resolve to a real predicate — not only the `**Label**`-headed case this report reproduces. ## Root Cause Analysis

Two layered causes, one primary and one pre-existing/documented:

1. **Primary — `classifyNodeBody` only pairs a title with a following list, never a following paragraph** (`internal/core/markdown.go:761-770`). `blockTitle` (`internal/core/markdown.go:1111`) happily recognizes `**Overview**` as a title regardless of what follows it, but the pairing `if` immediately re-checks the *next* sibling's concrete type against `*ast.List` only. A title followed by `*ast.Paragraph` fails that type assertion, so the `continue` is never reached; execution falls into the `switch v := children[idx].(type)` below, which reclassifies the title paragraph itself as plain `bodyBlockProse` — indistinguishable from real prose — and `idx` advances by one instead of two, so the following prose paragraph is *also* independently classified as `bodyBlockProse` on the next loop iteration. Both then flow through `walkNodeBody`'s positional leading/trailing accumulation (`internal/core/markdown.go:836-891`) with no schema-role resolution ever attempted, because `resolveLabelPredicate` is only called from the `bodyBlockTitled` branch (`internal/core/markdown.go:850`), which this shape never reaches.
2. **Secondary/pre-existing — `textPredicateFor`'s trailing slot is a type-blind `"notes"` for everything not otherwise named** (`internal/core/markdown.go:436-459`, specifically line 438: `if !leading { return "notes" }`). This was a known, explicitly-accepted gap from spec 023 BUG-001 (T068): CORE 0.12 retired `notes` from `Entity`/`Resource`'s Optional list, but no replacement trailing-prose key was introduced for those two types — the decision at the time was that lint flagging any use was an acceptable interim signal. Cause 1 is what routes `**Overview**`'s content into this already-known-fragile slot instead of its own, properly-resolved predicate name; cause 2 is why landing there is user-visible as a lint failure rather than a merely-cosmetic misclassification.

The rendering-order symptom is a direct, mechanical consequence of cause 1, not a separate defect: `renderNodeBody` already writes every named (non-reserved) `Texts` key before `renderEdges` (`internal/core/markdown.go:1266-1281` vs. `1286`); it is only because `Overview`'s content is keyed under the *reserved* trailing slot (`notes`) — written last, by design, per render-shape-contract.md step 6 — that it renders after `## Concerns` instead of before it, as any other named text-role predicate already would.
