# Bug Report: A text-role predicate's block renders with a `## Label` heading in `RenderNode` output, but ARCNET-CORE §5 requires a bold label in every format — the heading/bold split T097 copied from link-role predicates never applied to text-role ones

**Type**: Implementation drift (T097, spec 010's own BUG-003 fix, copied `renderEdges`'s link-role format-by-caller rule onto text-role predicates — a shape CORE §5 never asked for)
**Severity**: Medium
**Feature**: 010-predicate-node-model (FR-021, `renderNodeBody`'s "other Texts keys" loop)
**Reported**: 2026-09-05
**Status**: Resolved
**Patched**: 2026-09-05 — see spec.md FR-025, tasks.md Phase 10 (T112-T116).
**Resolved (implementation)**: 2026-09-05 — `writeText`'s "other Texts keys" call site (`internal/core/markdown.go`) now always renders `"**" + label + "**\n"`; the `if patchFormat` branch is removed for this call site only — `renderEdges`'s own, independent link-role heading/bold-by-caller logic is untouched. Corrected the stale comment and BUG-005's own new test assertion; added `TestRenderTextRolePredicateAlwaysBoldRegardlessOfFormat` confirming a text-role block stays bold in both `RenderNode`/`RenderPatch` while an adjacent link-role block still varies by caller. Audit found and fixed one pre-existing false assertion: `cmd/arc/graph/apply_test.go`'s `TestApplyLabeledBlockShapeSurvivesWikilinksListMarkersHeadingsAndGrouping` expected `## Assumptions` for a genuinely text-role predicate — corrected to `**Assumptions**`. `go build`, `go vet`, `go test ./...` all pass; manually re-verified via a real `arc init`/`arc apply` run.

## Description

`RenderNode`'s output for a named (non-primary) text-role predicate uses a `## Label` Markdown **heading**:

```markdown
# Title

*important text*

## Overview
Overview text

- derivedFrom:: [[document]]

## Concerns
- concerns:: [[repro-2026-bug005]]
```

ARCNET-CORE §5 states the opposite requirement, in the same sentence that establishes the leading/other text-role ordering this codebase already implements correctly:

> prose, from `text`-role predicates; Start with values from default `text` predicate and continue into other `text`-role predicates but prepend, **each block with bold, capital predicate name or its label**.

This is §5's own general node-body rule — not a patch-specific carve-out (that's §14.2.2, a separate clause). The correct output is:

```markdown
# Title

*important text*

**Overview**
Overview text

- derivedFrom:: [[document]]

## Concerns
- concerns:: [[repro-2026-bug005]]
```

Note `## Concerns` is unaffected and correct: `concerns` is a **link**-role predicate, and §5 separately specifies link-role groups use a `## Predicate` heading in a standalone node file (§14.2.2 gives link-role predicates the bold-label alternative specifically for patches, "since headings are reserved for type and identity there"). The heading-vs-bold split by caller format (`RenderNode` → `##`, `RenderPatch` → `**`) is real and correct, but it is a **link-role-only** rule — CORE never extends it to text-role predicates in either format.

## Root Cause Analysis

`renderNodeBody`'s `writeText` closure (`internal/core/markdown.go:1381-1397`) takes a `heading bool` and, when true, chooses `"**" + label + "**\n"` for `RenderPatch` (`patchFormat == true`) or `"## " + label + "\n"` for `RenderNode` (`patchFormat == false`) — exactly `renderEdges`'s own link-role group markup rule (`internal/core/markdown.go:1495` onward, correctly implementing CORE §14.2.2's "Link-role group markup by format" distinction, spec 013 BUG-001). `writeText` is called from two places: the leading/trailing reserved-slot writes (`heading: false`, unaffected) and the "other Texts keys" loop (`internal/core/markdown.go:1419-1421`, `heading: true`) — the latter is where every named **text**-role predicate's block is rendered, and it reuses the *same* `if patchFormat` branch `renderEdges` uses for **link**-role predicates.

This was introduced by T097 (spec 010's BUG-003 fix, 2026-07-21) under the explicit instruction to mirror `renderEdges`'s "role: link heading logic" — at the time, CORE's own §5 wording on this point may not have been checked, or was read as applying uniformly to "grouped" content regardless of role. CORE §5 in fact gives these two roles different rules: link-role groups vary by caller format (heading for a standalone node file, bold for a patch — because a patch's headings are reserved for `@type`/`@id` structure, per §14.2.2); text-role predicate blocks do not vary by caller format at all — they are always bold, in every format, because a bold label is simply how CORE distinguishes one named prose block from another within running body text, independent of whether headings happen to be free to use in that document.
